# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Project

A .NET-based Model Context Protocol (MCP) server for the [Google Health API](https://developers.google.com/health) (Fitbit and Pixel Watch data).

The driving use case: a Fitbit tracker or scale quietly builds up years of weight, activity, heart rate, sleep, and body-fat data, but it all sits behind Google's own app, cut off from everything else. This project exposes that data as read-only MCP tools so an LLM session can query it directly - "how did I sleep this week", "is my weight trending with body fat" - instead of scrolling through graphs. It's a standalone project: no other MCP server or account is required, and nothing here assumes a specific Fitbit device model (the driving hardware was a Fitbit Aria scale, but Google Health is the only real dependency, and Aria-model-specific assumptions have deliberately been kept out of the docs and tool descriptions since not every user has one).

  3. After both fixes, `auth login` succeeded and a live call returned real weight data (11 days of August readings, 99–102 kg range) correctly parsed and converted to kg.
- **Tool coverage** (`src/FitbitMcp/Tools/`): just `WeightTools.GetWeightHistory` (`get_weight_history`), deliberately scoped to only the first data type — no Activity/Sleep/HeartRate/Nutrition tools, no legacy Fitbit Web API integration (that's Milestone 2, issues #4–#6).
- **Auth implementation** (`src/FitbitMcp/Auth/`): OAuth 2.0 authorization-code + PKCE (`GoogleHealthOAuth2Client`), a loopback-listener CLI bootstrap (`AuthCli`, `dotnet run -- auth login`), and a `TokenStore` that reads/writes this project's `dotnet user-secrets` backing file directly rather than a separate dotfile convention. `GoogleHealthApi` refreshes automatically on 401 or stored expiry. The Google Cloud OAuth client must be **Web application** type (not Desktop) with `http://127.0.0.1:3000/callback` registered exactly under Authorized redirect URIs — this code uses a fixed port+path, not Google's dynamic-loopback-port exception for Desktop-type clients.
- **Infrastructure**: dual stdio/HTTP transport (stdio default, `--http` flag), `dotnet tool` packaging (`fitbit-mcp` command), Nerdbank.GitVersioning for automatic semantic versioning, an explicit `AddUserSecrets<Program>()` fix so secrets still load outside `ASPNETCORE_ENVIRONMENT=Development`.
- **Tests**: `tests/FitbitMcp.Tests` (NUnit), 7 tests covering `GoogleHealthOAuth2Client` (authorize-URL building, code exchange, refresh, error handling — via a stub `HttpMessageHandler`, no network) and `WeightTools.ParseEntries` (now matching the confirmed-live `rollupDataPoints` shape). `.github/workflows/build.yml` runs restore/build/test on push and PR to `main`.

## Architecture plan

- **MCP transport**: official [ModelContextProtocol C# SDK](https://github.com/modelcontextprotocol/csharp-sdk) (`ModelContextProtocol.AspNetCore`). Dual transport, chosen at startup by branching on `args`: stdio (default, `Host.CreateApplicationBuilder` + `WithStdioServerTransport`) or HTTP (`--http`, `WebApplication.CreateBuilder` + stateless Streamable HTTP via `MapMcp`) — the SDK can't register both transports on one builder, so the branch happens before either is configured.
- **Auth**: OAuth 2.0 authorization-code + PKCE (Google's standard flow), config-driven with nothing committed to the repo.
- **Target framework**: `net10.0` (also multi-targets `net8.0` for the published package - see below). Packable as a `dotnet tool` (`PackAsTool`).
- **Deferred**: legacy Fitbit Web API (activity/sleep/heart rate/nutrition) as a second data path (Milestone 2). No abstraction layer (e.g. `IHealthDataProvider`) has been introduced yet — deliberately not built speculatively ahead of a second real implementation to abstract over (see #6).
- **Cloud multi-tenant deployment**: design sketch only, not implemented — see [docs/cloud-deployment.md](docs/cloud-deployment.md). Covers running an invite-only beta (Google's OAuth "Testing" mode allowlist doubles as the invite mechanism), per-user token storage, and MCP-level bearer auth, while leaving this single-user dev mode untouched. Tracked as the "Cloud multi-tenant service" milestone.

## Status update, 2026-08-19 (continued again) - dropped the FatSecret cross-project framing

Earlier status entries above described this project's origin partly in terms of syncing weight into a companion FatSecret-tracking MCP server, and its example use-cases referenced comparing against FatSecret directly. That framing is gone as of this pass:

- **Why**: fitbit-mcp and any FatSecret-facing server are independent projects with no shared code or credentials. The cross-project sync path (writing Google Health weight into FatSecret) hit a hard platform ceiling — FatSecret's own API refuses to backdate entries more than ~2 days, discovered live and undocumented on FatSecret's side — so it never became reliable functionality, and this project shouldn't keep advertising it as a reason to exist.
- **What changed**: the README's Purpose section, Status table, and top-line description no longer mention FatSecret or any sync feature; the "driving use case" in this file's Project section is now Google Health data access on its own terms. `WeightTools.GetWeightHistory`'s tool description and the top-line README description no longer name the Aria scale model specifically (it's not sold anymore and may be EOL) — Google Health, not a specific Fitbit device, is the only real dependency. `AuthCli`'s doc comment no longer compares Google's OAuth flow to FatSecret's OAuth1 flow.
- **What didn't change**: the underlying auth/data-fetching code is untouched — this was a docs-and-framing pass, not a functional one. All tests still pass; no tool signatures changed.

## Status update, 2026-08-20 (continued again) - new `get_exercise_history` tool

The structurally bigger piece flagged as deferred in the previous two passes: individual exercise/workout sessions, not another daily-rollup field.

- **New session-shaped tool** (`ExerciseTools.GetExerciseHistory`), following the `SleepTools` pattern (`ListDataPointsAsync`, not a rollup) since `exercise` is Google Health's other session data type. Confirmed via the live discovery doc's `Exercise`/`MetricsSummary`/`ExerciseMetadata` schemas and the `dataPoints.list` filter documentation - not guessed.
- **Real finding that changes the filter from the sleep pattern**: the discovery doc's filter syntax explicitly scopes `{session_data_type}.interval.civil_end_time` filtering to "Sleep specific" and documents `{session_data_type}.interval.civil_start_time` as the general session filter ("Excluding Sleep and ECG"). So `get_exercise_history` filters and dates entries by session **start**, unlike `get_sleep_history`'s wake-up-date-based `civil_end_time` filter - copying sleep's filter verbatim would have silently returned wrong/no results.
- **Answers the "GPS route data" question directly, with a real answer, not a guess**: `Exercise`'s only GPS-related field is `ExerciseMetadata.hasGps` (a boolean - "whether the exercise had GPS tracking"). There is no route/polyline/waypoint field anywhere in the `Exercise` schema. Raw GPS coordinates are not part of this data type at all - confirmed by reading the full schema, not inferred from a missing field. `get_exercise_history` surfaces `hasGps` as-is; getting an actual route would need a different, more sensitive data type/scope entirely (`location`), which is out of scope for this tool.
- **Fields returned**: `{ date, displayName, exerciseType, durationMinutes, distanceKm, caloriesKcal, averageHeartRateBpm, averagePaceMinPerKm, elevationGainMeters, steps, hasGps }`. `durationMinutes` prefers `activeDuration` (excludes pauses) and falls back to the raw interval span when `activeDuration` is absent. `averagePaceSecondsPerMeter` is converted to the more familiar minutes/km. Distance (mm) and elevation gain (mm) are converted to km/m respectively, matching the unit-conversion pattern already used for `distance` in `get_activity_summary`. Same 25-session-per-call cap and default as `get_sleep_history` (confirmed in the discovery doc: `exercise` and `sleep` share the same max/default page size).
- Same `activity_and_fitness.readonly` scope already granted - no re-auth needed (confirmed via the discovery doc's per-endpoint scopes list for `dataPoints.list`).
- 4 new tests (24 total): `ExerciseToolsTests` covering the full-field happy path, the `activeDuration`-absent fallback, missing-interval skip, and empty-response.
- **Verified live** via the standalone stdio script: pulled August and July, both months returned real, varied sessions (running, biking, walking, soccer, motorcycling) with plausible distance/calories/heart-rate/pace values, and `hasGps: true` correctly appearing on GPS-tracked sessions (mostly biking/running) vs `null` on manually-logged types like soccer.
- **Not yet in a published package**: same as the other recent additions - only exists in source until the next nuget.org release.
