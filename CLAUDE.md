# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Project

A .NET-based Model Context Protocol (MCP) server for the [Google Health API](https://developers.google.com/health) (Fitbit and Pixel Watch data). Built as a sibling project to [fatsecret-mcp](../fatsecret-mcp), following the same conventions (solution layout, license, tooling, NUnit, MCP tool patterns).

The driving use case: the developer's Fitbit Aria 2 scale syncs weight into Google Health, but that weight never makes it into FatSecret (activity already syncs Fitbit → FatSecret; weight doesn't). fatsecret-mcp already has `get_weight_history`/`add_weight_entry` tools. This project's job is to expose the Google Health side — a read-only weight tool — so a Claude session with both MCP servers connected can compare the two and fill in what's missing, with neither server needing the other's credentials.

## Status as of 2026-08-18 (end of first working session)

**The prototype is done and the core question has been answered — with an important caveat found along the way.**

- Pushed to GitHub: [mregen/fitbit-mcp](https://github.com/mregen/fitbit-mcp), public, branch `main`. MIT licensed (`LICENSE` + SPDX headers per source file).
- **Auth and `get_weight_history` both work against the real account.** Getting there took two rounds of fixing wrong guesses:
  1. First `auth login` attempt failed with Google's `invalid_scope` error — the scope this code requested (`googleapis.com/auth/health.rollup`) doesn't exist; it was a guess from a REST reference *page* rather than the actual API contract.
  2. Pulled the live discovery document (`https://health.googleapis.com/$discovery/rest?version=v4`) to get the real scope (`googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly`) and, while there, found the `dataPoints:rollUp` request/response shape was also wrong (modeled on the legacy Google Fit v1 aggregate API — nested `bucket`/`dataset`/`point`/`value` — instead of v4's actual flat `{ rollupDataPoints: [{ startTime, weight: { weightGramsAvg } }] }`, in grams not kg).
  3. After both fixes, `auth login` succeeded and a live call returned real weight data (11 days of August readings, 99–102 kg range) correctly parsed and converted to kg.
- **Ran the actual end-to-end comparison against fatsecret-mcp for August**: 8 of 11 Google Health days were missing from FatSecret; the 3 present were off by 0.1–0.35 kg (Fitbit's native device sync uses a single reading, Google Health's rollup is a full-day average — a methodology difference, not an error on either side).
- **Known limitation, discovered live, not a bug in this codebase**: attempted to backfill all 11 missing/mismatched days via fatsecret-mcp's `add_weight_entry`. Every call failed with FatSecret error 205 — *"Date must be within 2 days from today"* — undocumented on FatSecret's own `weight.update` reference page. **This API cannot backfill historical weight data at all**, no matter which MCP server drives it. The sync approach only works for weigh-ins within the last ~2 days; anything older needs manual entry through FatSecret's own app. Full write-up on issue #3 (closed) and a follow-up filed as #11 (never actually confirmed a *successful* write, since nothing in scope was in-window that day).
- **Tool coverage** (`src/FitbitMcp/Tools/`): just `WeightTools.GetWeightHistory` (`get_weight_history`), deliberately scoped to only the first use case — no Activity/Sleep/HeartRate/Nutrition tools, no legacy Fitbit Web API integration (that's Milestone 2, issues #4–#6).
- **Auth implementation** (`src/FitbitMcp/Auth/`): OAuth 2.0 authorization-code + PKCE (`GoogleHealthOAuth2Client`), a loopback-listener CLI bootstrap (`AuthCli`, `dotnet run -- auth login`), and a `TokenStore` that reads/writes this project's `dotnet user-secrets` backing file directly rather than a separate dotfile convention. `GoogleHealthApi` refreshes automatically on 401 or stored expiry. The Google Cloud OAuth client must be **Web application** type (not Desktop) with `http://127.0.0.1:3000/callback` registered exactly under Authorized redirect URIs — this code uses a fixed port+path, not Google's dynamic-loopback-port exception for Desktop-type clients.
- **Infrastructure parity with fatsecret-mcp** (separate earlier pass this session): dual stdio/HTTP transport (stdio default, `--http` flag), `dotnet tool` packaging (`fitbit-mcp` command), Nerdbank.GitVersioning for automatic semantic versioning, an explicit `AddUserSecrets<Program>()` fix so secrets still load outside `ASPNETCORE_ENVIRONMENT=Development`.
- **Tests**: `tests/FitbitMcp.Tests` (NUnit), 7 tests covering `GoogleHealthOAuth2Client` (authorize-URL building, code exchange, refresh, error handling — via a stub `HttpMessageHandler`, no network) and `WeightTools.ParseEntries` (now matching the confirmed-live `rollupDataPoints` shape). `.github/workflows/build.yml` runs restore/build/test on push and PR to `main`.

## Architecture plan

- **MCP transport**: official [ModelContextProtocol C# SDK](https://github.com/modelcontextprotocol/csharp-sdk) (`ModelContextProtocol.AspNetCore`). Dual transport, chosen at startup by branching on `args`: stdio (default, `Host.CreateApplicationBuilder` + `WithStdioServerTransport`) or HTTP (`--http`, `WebApplication.CreateBuilder` + stateless Streamable HTTP via `MapMcp`) — same pattern as fatsecret-mcp, since the SDK can't register both transports on one builder.
- **Auth**: OAuth 2.0 authorization-code + PKCE (Google's standard flow), simpler than fatsecret-mcp's OAuth1 three-legged flow but still config-driven with nothing committed to the repo.
- **Sync mechanism is deliberately not code**: no bespoke sync tool/pipeline lives in this repo or fatsecret-mcp. The "does it match / fill in gaps" work happens live, in a Claude session with both MCP servers connected, by calling each server's own tools. This keeps the two servers independent (neither holds the other's credentials) and avoids building automation for what turned out to have a hard platform ceiling (FatSecret's 2-day backdate limit) anyway — no amount of in-repo automation would work around that.
- **Target framework**: `net10.0`, matching fatsecret-mcp. Also packable as a `dotnet tool` (`PackAsTool`), matching fatsecret-mcp.
- **Deferred**: legacy Fitbit Web API (activity/sleep/heart rate/nutrition) as a second data path (Milestone 2). No abstraction layer (e.g. `IHealthDataProvider`) has been introduced yet — deliberately not built speculatively ahead of a second real implementation to abstract over (see #6).
- **Cloud multi-tenant deployment**: design sketch only, not implemented — see [docs/cloud-deployment.md](docs/cloud-deployment.md). Covers running an invite-only beta (Google's OAuth "Testing" mode allowlist doubles as the invite mechanism), per-user token storage, and MCP-level bearer auth, while leaving this single-user dev mode untouched. Tracked as the "Cloud multi-tenant service" milestone.

## Status update, 2026-08-19

- **Issue #11 closed**: fetched today's real weight from Google Health (101.4 kg), confirmed it was missing from FatSecret, wrote it via `add_weight_entry`, and re-verified it landed correctly. This is the first confirmed *successful* write — the ongoing (not historical) sync case is now proven end to end. All of Milestone 1 (#1, #2, #3, #11) is closed.
- Sketched a cloud multi-tenant deployment design (see above) after being asked whether this could be hosted for multiple invited users. Also answered, inline in conversation (not yet in a design doc), whether more Google Health data types (activity/heart-rate, sleep, body-fat, etc.) or write access are reachable — yes to both, via additional scopes, but explicitly deferred as separate future work.
- **Added read-only activity, heart-rate, and sleep tools** (`get_activity_summary`, `get_heart_rate_history`, `get_sleep_history`), picking the three data types with the best cost/value for an LLM assistant (steps/calories/active-minutes, heart rate, sleep — chosen over body-fat/blood-glucose/ECG/location/reproductive-health as higher general interest; body-fat was the one free add — same scope as weight — but wasn't requested this round). **This is Google Health data, not the legacy Fitbit Web API** — issues #4–#6 (legacy Fitbit phase) are untouched and still not started; don't conflate the two.
  - `GoogleHealthApi` generalized: `GetRollupAsync(dataTypeId, start, end)` replaces the weight-specific `GetWeightRollupAsync`, plus a new `ListDataPointsAsync(dataTypeId, filter)` for session-shaped types (sleep) that don't have a rollup value at all — confirmed via the discovery doc that `sleep` is absent from `RollupDataPoint`'s field union, comes back via `dataTypes.dataPoints.list` + a `sleep.interval.civil_end_time` filter instead, returning full `DataPoint.sleep.summary` objects (`minutesAsleep`/`minutesAwake`/`minutesInSleepPeriod`).
  - Steps → `StepsRollupValue.countSum`; total calories → `TotalCaloriesRollupValue.kcalSum`; active minutes → `ActiveMinutesRollupValue`'s per-activity-level breakdown, summed into one daily total; heart rate → `HeartRateRollupValue`'s avg/min/max. `get_activity_summary` makes three parallel rollup calls (steps/total-calories/active-minutes — Google has no multi-type rollup request) and merges them by date; the merge logic (`ActivityTools.MergeEntries`) is a pure, independently-tested function.
  - **Real, confirmed API constraint**: heart-rate, active-minutes, total-calories (and calories-in-heart-rate-zone) cap rollup queries at a 14-day range; other rollup types (weight, steps) allow 90 days. `get_activity_summary`/`get_heart_rate_history` both default to the last 14 days for consistency, rather than mixing different max ranges per sub-metric.
  - **Scope change requires re-auth**: `GoogleHealthOAuth2Client.Scope` now requests `health_metrics_and_measurements.readonly activity_and_fitness.readonly sleep.readonly` (space-separated, multi-scope). Confirmed live against the account's existing (weight-only) tokens: both new tools fail with a clean Google 403 — `MISSING_OAUTH_SCOPE`, `any_of_required: activity_and_fitness_readonly` / `sleep_readonly` — proving the request plumbing is correct and only the missing scope blocks it. **Re-running `auth login` to pick up the new scopes is the next required step** before any of the three new tools can be exercised against real data; none of their response-parsing has been verified live yet (same "confirmed against the discovery doc, not yet a real call" caveat that weight went through first).
  - 7 new tests (14 total): `ActivityToolsTests` (2), `HeartRateToolsTests` (2), `SleepToolsTests` (3) — all hand-written JSON matching the discovery-doc schema, no live calls.
  - **Re-authed and verified live the same day (issue #16, closed)**: all three tools returned correct, plausible data on the first real call — no schema-mismatch surprises this time, unlike weight's two rounds of fixes. `get_weight_history` also re-checked working post-re-auth (token refresh handled the new scope transparently). One real finding, filed as #17: a day with both a nap and a main sleep session returns two ambiguous same-date entries from `get_sleep_history`, since Google's `SleepMetadata.mainSleep`/`nap` flags aren't surfaced yet.

## Status update, 2026-08-19 (continued) - consuming-project verification and `get_body_fat_history`

Verified end-to-end from the client side (the `fatsecret` project's Claude Code session, not this repo) - the first time this tool has been exercised as an installed package rather than run from source:

- **Found a real breakage**: the consuming project's MCP registration used the old source-checkout pattern (`dotnet run --project ... --no-launch-profile`). Once this repo started multi-targeting `net8.0;net10.0`, that bare `dotnet run` became ambiguous ("Your project targets multiple frameworks") and failed immediately on launch - surfaced to the MCP client only as a generic `-32000 Connection closed`, with no hint of the real cause. Root-caused by running the same command directly in a shell, where the actual .NET error was visible.
- **Fix**: switched the consuming registration to the installed global tool (`~/.dotnet/tools/fitbit-mcp`), passing `GoogleHealth__ClientId`/`GoogleHealth__ClientSecret` as env vars per this README's documented Claude Code setup - matching how `fatsecret-mcp` is already registered in that project.
- **Confirmed the `UserSecretsId` bridge works as designed**: the globally-installed tool picked up the existing refresh token from the same `secrets.json` the source project's `dotnet user-secrets` had been managing, with no fresh `auth login` needed after the switch.
- **Live-verified against the real account, from outside this repo for the first time**: `get_sleep_history` (a full week of real nights, including the known dual-entry nap/main-sleep case from #17), `get_activity_summary` (14 days of steps/calories/active-minutes, zero errors), and `get_weight_history` (six months of 2026 data pulled across multiple monthly calls) all returned correct data on every call. This corroborates the 2026-08-19 "re-authed and verified live" status above (issue #16) from a second, independent client.
- **Gap surfaced by real use, closed the same session**: a request for body-fat percentage alongside weight had no tool to serve it - `get_weight_history` only returns `{ date, weightKg }`. Body fat shares weight's OAuth scope (noted above as "the one free add"), so a dedicated tool was quick to add:
  - New `BodyFatTools.GetBodyFatHistory` (`get_body_fat_history`), same month-scoped shape as `get_weight_history`. Confirmed via the live discovery doc (not guessed): `RollupDataPoint.bodyFat` → `BodyFatRollupValue.bodyFatPercentageAvg`, `dataTypeId` = `body-fat`. Already a percentage value - no unit conversion needed (unlike weight's grams-to-kg).
  - Uses the shared `RollupParsing.Enumerate` helper (same pattern as `HeartRateTools`), rather than the bespoke `JsonDocument` walk in `WeightTools` (written before that helper existed). Same OAuth scope as weight - no new scope, no re-auth needed for accounts already authorized for weight.
  - 3 new tests (17 total): `BodyFatToolsTests`, mirroring `WeightToolsTests`' three cases (flattens rollup points, skips windows without the value, empty response). Full suite passes (`dotnet test`).
  - **Verified live the same session**, tested outside the normal MCP-client path (the installed nuget package doesn't have this tool yet - only source does): spawned the source build directly (`dotnet run --framework net10.0 --project src/FitbitMcp --no-launch-profile`) and drove it with a standalone script speaking raw MCP stdio JSON-RPC (`initialize` → `notifications/initialized` → `tools/call`), bypassing the consuming project's live registration entirely so it didn't have to be disturbed mid-session. Real calls to `POST /v4/users/me/dataTypes/body-fat/dataPoints:rollUp` returned `200` with correctly parsed percentages across single days and a full six-month pull (Jan-Jun 2026, one call per month) - no schema-mismatch surprises, unlike weight's two rounds of fixes. README status table updated from "not yet exercised" to "✅ Working, verified live" to match.
  - **Not yet in a published package**: this tool only exists in source until the next `dotnet tool install --global FitbitMcp` after a new nuget.org release (manual `workflow_dispatch`, account-owner action - see the Publishing note above).
